## 1. เรากำลังประเมินอะไร

โมเดล **DentexSegAndDet v1.0** ที่ใช้จริงใน `app/services/ai_inference.py`
ทำงาน 2 ขั้นต่อกัน (two-stage pipeline):

```
รูป X-ray พาโนรามิก
      │
      ├─► ขั้นที่ 1: SEUNet  ─── แบ่งพื้นที่ฟันออกเป็น 32 ซี่ (FDI 11-48)
      │                          ได้ mask ที่ระบุว่าพิกเซลไหนเป็นฟันซี่ไหน
      │
      ├─► ขั้นที่ 2: YOLOv8x ─── ตรวจหาโรค 4 ชนิดเป็นกรอบสี่เหลี่ยม
      │                          Impacted, Caries, Periapical Lesion, Deep Caries
      │
      └─► ขั้นที่ 3: Post-processing ─── จับคู่กรอบโรคเข้ากับซี่ฟัน
                                        โดยดูว่ากรอบทับ mask ของฟันซี่ไหนมากที่สุด
                                        ฟันที่ไม่มีโรค → is_healthy = true
```

ผลลัพธ์ทั้งหมดถูกเก็บลงคอลัมน์ `ai_detection_analysis.detection_data`

**สิ่งสำคัญ:** เราประเมิน _โค้ดที่ deploy จริง_ ไม่ได้เขียนโค้ดประเมินแยกต่างหาก
ทุกการวัดเรียกผ่าน `ai_inference.predict()` ตัวเดียวกับที่ backend ใช้

## 3. เรื่องที่สำคัญที่สุด: Data Leakage

### ปัญหาคืออะไร

โมเดลถูกเทรนด้วยรูปชุดหนึ่ง ถ้าเราเอา**รูปเดิมนั้น**มาทดสอบ
มันก็เหมือนให้นักเรียนทำข้อสอบที่เคยเห็นเฉลยแล้ว — คะแนนสวยแต่ไม่มีความหมาย

ศัพท์เทคนิคเรียกว่า **data leakage** และมันคือกับดักอันดับหนึ่งของการประเมินโมเดล

### มันเกิดขึ้นกับเราจริง

รอบแรกที่รัน เราไม่รู้ว่ารูปไหนเคยถูกใช้เทรน เลยสุ่มมา 106 รูปจาก 705 รูป
ผลที่ได้คือ:

| Metric               | รอบแรก (ปนข้อมูลเทรน) | รอบจริง (held-out) | ต่าง                |
| -------------------- | --------------------- | ------------------ | ------------------- |
| mAP@0.5              | 0.6961                | 0.4493             | **-0.25**           |
| F1 Periapical Lesion | 0.667                 | 0.333              | **หายไปครึ่งหนึ่ง** |
| Mean IoU             | 0.7430                | 0.6587             | -0.08               |
| Enumeration Accuracy | 0.9643                | 0.8613             | -0.10               |

ถ้าเชื่อตัวเลขรอบแรกแล้วเขียนลงเอกสาร = **รายงานเกินจริงเกือบทุกตัว**

### แก้ยังไง — YOLO (ฝั่งตรวจโรค)

ต้องรู้ว่ารูปไหนคือ "ข้อสอบที่ไม่เคยเห็น" ซึ่งอยู่ในไฟล์ที่สร้างตอนเทรน:

```
instances_train2017.json   564 รูป  ← ใช้เทรน
instances_val2017.json     141 รูป  ← กันไว้ทดสอบ (held-out)
                          ───────
                           705 รูป  = ครบพอดี ไม่ทับกันเลย
```

ไฟล์นี้**ไม่ได้อยู่ใน Kaggle** — มันถูกสร้างบนเครื่องที่เทรน
โชคดีที่ยังหาเจอ เลยใช้ 141 รูปนั้นเป็นชุดทดสอบจริง

### แก้ยังไง — SEUNet (ฝั่งแบ่งซี่ฟัน)

ของ SEUNet ไม่มีไฟล์ split แต่**ไม่ต้องหา** เพราะโค้ดเทรนแบ่งด้วย seed คงที่:

```python
# train_unet.py
train_dataset, val_dataset = torch.utils.data.random_split(
    dataset, [train_size, val_size],
    generator=torch.Generator().manual_seed(args.seed)   # default = 42
)
```

seed คงที่ = สุ่มแบบเดิมทุกครั้ง = **คำนวณย้อนกลับได้**
เราจึงสร้าง split เดิมขึ้นมาใหม่ได้จากไฟล์ Kaggle ล้วนๆ → 507 เทรน / 127 ทดสอบ

### แต่เราไม่เชื่อตัวเอง — ต้องพิสูจน์

การ reconstruct ตั้งอยู่บนสมมติฐานว่า "ตอนเทรนใช้ seed=42" ถ้าสมมติฐานผิด
เราจะได้ split มั่วแล้วเคลมว่าสะอาด ซึ่งคือความผิดพลาดที่พยายามเลี่ยงมาตลอด

วิธีพิสูจน์: **วัดทั้งสองฝั่งแล้วเทียบกัน**

| ชุด                         | Mean IoU    |
| --------------------------- | ----------- |
| ฝั่งที่คำนวณว่าเป็น "เทรน"  | 0.7701      |
| ฝั่งที่คำนวณว่าเป็น "ทดสอบ" | 0.6587      |
| **ส่วนต่าง**                | **+0.1114** |

โมเดลย่อมทำได้ดีกว่ากับรูปที่เคยเห็น — ส่วนต่างขนาดนี้ยืนยันว่า split ที่คำนวณ**ตรงกับของจริง**
ถ้า reconstruct ผิด สองฝั่งจะเป็นแค่การสุ่มสองกอง ผลจะไม่ต่างกัน

## 4. Metric แต่ละตัวหมายความว่ายังไง

### IoU (Intersection over Union) — พื้นฐานของทุกอย่าง

วัดว่ากรอบ/พื้นที่ 2 อันทับกันแค่ไหน

```
IoU = พื้นที่ที่ทับกัน / พื้นที่รวมทั้งหมด

ค่า 1.0 = ทับสนิท        ค่า 0 = ไม่ทับเลย
เกณฑ์มาตรฐาน IoU ≥ 0.5 ถือว่า "ตรวจเจอ"
```

### mAP (mean Average Precision) — ใช้กับ AITC-01

วัดคุณภาพการตรวจจับโดยรวม คิดจากพื้นที่ใต้กราฟ Precision-Recall

- **mAP@0.5** — นับว่าเจอเมื่อกรอบทับ ≥ 50%
- **mAP@0.5:0.95** — เข้มกว่า เฉลี่ยตั้งแต่เกณฑ์ 50% ถึง 95% (ต้องวางกรอบแม่นมาก)

> **จุดที่เราแก้ Test Plan:** เดิม §5.2 บอกให้วัดทุกอย่างที่ conf = 0.25
> แต่ mAP **นิยามคือพื้นที่ใต้กราฟทั้งเส้น** การตัดที่ 0.25 คือตัดหางกราฟทิ้ง
> ได้ตัวเลขที่เทียบกับงานวิจัยอื่นไม่ได้ และต่ำกว่าความจริง
>
> | วิธีวัด                 | mAP@0.5    |
> | ----------------------- | ---------- |
> | เต็มเส้น (มาตรฐาน COCO) | **0.5290** |
> | ตัดที่ conf 0.25        | 0.4493     |
>
> เราจึงแยกเป็น 2 protocol: **mAP วัดเต็มเส้น** ส่วน metric ที่ขึ้นกับ threshold
> (F1, assignment, robustness) **วัดที่ 0.25 ตามที่ deploy จริง**

### Precision / Recall / F1 — ใช้กับ AITC-01

```
Precision = ที่ทายว่าเป็นโรค ถูกกี่ %     (ทายมั่วเยอะ → ต่ำ)
Recall    = โรคที่มีจริง เจอกี่ %          (มองข้ามเยอะ → ต่ำ)
F1        = ค่าเฉลี่ยถ่วงของสองตัว
```

ในบริบททันตกรรม:

- **Precision ต่ำ** = บอกว่าฟันดีเป็นฟันผุ → คนไข้ถูกรักษาเกินจำเป็น
- **Recall ต่ำ** = มองข้ามฟันที่ผุจริง → คนไข้ไม่ได้รับการรักษา

### Mean IoU / Enumeration Accuracy — ใช้กับ AITC-02

- **Mean IoU** — mask ฟันที่โมเดลวาด ทับกับของจริงเฉลี่ยกี่ %
- **Enumeration Accuracy** — ฟันกี่ % ที่โมเดลทั้งหาเจอ**และ**ใส่เลข FDI ถูก (IoU ≥ 0.5)

### Assignment Accuracy — ใช้กับ AITC-03

โรคที่ตรวจเจอ ถูกจับคู่เข้ากับ**ซี่ฟันที่ถูกต้อง**กี่ %

> **ข้อควรรู้:** เรานับเฉพาะ detection ที่ YOLO หาเจอถูกแล้ว (ทับ ground truth ≥ 0.5)
> เพราะถ้า YOLO ตรวจไม่เจอตั้งแต่แรก นั่นคือความผิดของ AITC-01
> ไม่ควรโดนหักซ้ำที่ AITC-03

### ทำไมเกณฑ์บางตัวถูกปรับ

> รายละเอียดเต็ม + คำตอบเวลาโดนถามเจาะ ดูที่ [`THRESHOLDS.th.md`](THRESHOLDS.th.md)

เกณฑ์เดิมตั้งไว้ก่อนมีข้อมูลจริง พอวัดบน held-out แล้วพบว่าบางตัว
**โมเดลไม่เคยทำได้เลยไม่ว่า threshold ไหน** — เกณฑ์ที่ไม่มีวันผ่านไม่ได้วัดอะไร

| Metric               | เดิม   | ใหม่       | เหตุผล                          |
| -------------------- | ------ | ---------- | ------------------------------- |
| F1 Impacted          | ≥ 0.50 | **≥ 0.80** | เกณฑ์เดิมหลวมไป โมเดลทำได้ 0.88 |
| F1 Caries            | ≥ 0.50 | ≥ 0.45     | เพดานจริง ~0.47 ทุก threshold   |
| F1 Periapical Lesion | ≥ 0.50 | ≥ 0.30     | เพดานจริง ~0.35                 |
| Mean IoU             | ≥ 0.70 | ≥ 0.65     | 0.70 ผ่านได้เฉพาะตอนมี leakage  |
| Enumeration Acc      | ≥ 0.90 | ≥ 0.85     | เช่นเดียวกัน                    |

หลักการ: ตั้งเกณฑ์**ต่ำกว่าที่วัดได้จริงเล็กน้อย** เพื่อให้ทำหน้าที่เป็น
_regression guard_ — ถ้าวันหน้าแก้โค้ดแล้วโมเดลแย่ลง test จะจับได้ทันที
(สังเกตว่า Impacted ถูก**ยกขึ้น** ไม่ใช่ลดอย่างเดียว)

### หลักฐานว่าเราคำนวณถูก

ตัวเลขของเราเทียบกับ log ตอนเทรนของ ultralytics บนรูปชุดเดียวกัน:

|                        | mAP@0.5 | mAP@0.5:0.95 |

คนละ implementation แต่ได้ใกล้กันมาก = **โค้ดคำนวณ metric ของเราถูกต้อง**

## 8. ข้อจำกัดที่ควรเขียนลงเอกสาร

1. **Periapical Lesion มีตัวอย่างน้อยมาก** — ในชุดทดสอบมีแค่ 18 กรอบ
   F1 = 0.333 จากตัวอย่างเท่านี้มี error bar กว้าง ทายถูกเพิ่ม 1 กรอบเปลี่ยน F1 ไป ~0.04
   ควรระบุว่าเป็นตัวเลขเบื้องต้น

2. **Caries precision ต่ำ (0.407)** — ทายผิด 355 ครั้ง เทียบกับถูก 244 ครั้ง
   ในทางคลินิกคือแนวโน้ม over-diagnosis เป็นจุดที่ควรปรับปรุงมากที่สุด

3. **Deep Caries recall ต่ำ (0.425)** — พลาดไปมากกว่าครึ่ง
   ทั้งที่เป็นภาวะรุนแรงกว่า Caries ธรรมดา

4. **SEUNet ย่อรูปเหลือ 256×256** ก่อนแบ่งฟัน จากต้นฉบับ ~2800×1316
   แล้วขยายกลับ ทำให้ขอบ mask หยาบ กิน IoU ไปตรงๆ
   ถ้าเทรนที่ความละเอียดสูงขึ้นน่าจะดีขึ้นจริง

5. **ชุดทดสอบ 141 รูป (20%) ไม่ใช่ 15% ตามที่ §5.2 เขียนไว้เดิม**
   เพราะเราเลือกใช้ split จริงจากตอนเทรน ซึ่งสำคัญกว่าการให้ได้จำนวนตามที่กำหนด

6. **ประเมินบน DENTEX ซึ่งเป็นข้อมูลต่างประเทศ** ยังไม่ได้ทดสอบกับ X-ray
   จากเครื่องและกลุ่มประชากรที่จะใช้งานจริง

---

## 9. สรุปสั้นๆ

สิ่งที่ทำไปคือ:

1. สร้างเครื่องมือวัดที่ทดสอบตัวเองได้ (มี unit test คุมทุกโมดูล รันได้โดยไม่ต้องมี dataset)
2. ค้นพบว่ารอบแรกวัดบนข้อมูลที่โมเดลเคยเห็น ตัวเลขสูงเกินจริง
3. หา split จริงของ YOLO กลับมาได้ และ**คำนวณ split ของ SEUNet ย้อนกลับ**จาก seed
4. พิสูจน์ว่า split ที่คำนวณถูกต้อง ด้วยการเทียบผลระหว่างฝั่งเทรนกับฝั่งทดสอบ
5. ตรวจสอบว่าโค้ดคำนวณ metric ถูก ด้วยการเทียบกับ log ตอนเทรน
6. ปรับเกณฑ์ให้สอดคล้องความจริง พร้อมเหตุผลกำกับทุกตัว

**คุณค่าของงานนี้อยู่ที่วิธีการมากกว่าตัวเลข** — ตัวเลขที่ตรวจสอบย้อนกลับได้
และรู้ข้อจำกัดของตัวเอง มีน้ำหนักกว่าตัวเลขสวยที่พิสูจน์ไม่ได้
